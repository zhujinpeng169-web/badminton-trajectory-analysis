# 羽毛球 + 运动员轨迹可视化系统 —— 实现解析

> 本文档剖析本项目从原始视频到最终分析成片的完整实现，便于后续维护与向 AI+VR 方向扩展。
> 对应代码：`external/TrackNetV3/`（羽毛球）、`pipeline_code/overlay_player_analytics.py`（运动员 + 渲染）。

---

## 一、整体架构：两个独立模型 + 一个渲染层

本系统**不是**端到端单模型，而是**两条独立感知管线**最后在渲染脚本里融合：

```
                  ┌─────────────────────────────────────────┐
   原始视频 41.MP4 │                                           │
        │         │  管线A: TrackNetV3 (羽毛球轨迹)            │
        ├────────►│  external/TrackNetV3/predict.py           │──► 41_ball.csv
        │         │                                           │   (每帧球的 X,Y,可见性)
        │         └─────────────────────────────────────────┘
        │
        │         ┌─────────────────────────────────────────┐
        └────────►│  管线B + 渲染层 (运动员轨迹 + 叠加)         │──► 41_analysis.mp4
                  │  pipeline_code/overlay_player_analytics.py │   (最终成片)
                  │  读入 41.mp4 + 41_ball.csv                 │
                  └─────────────────────────────────────────┘
```

**关键认知**：羽毛球和运动员用**完全不同的检测原理**，方案不通用。
- 羽毛球：又小又快、会运动模糊 → 用「热力图分割」范式（TrackNet）。
- 运动员：大、慢、形状稳定 → 用「目标检测 + 多目标跟踪」范式（YOLO + ByteTrack）。

## 二、管线A：羽毛球轨迹（TrackNetV3）—— 热力图范式

### 2.1 核心思想：把"检测"变成"图像分割"

`external/TrackNetV3/model.py` 是一个 **U-Net 编码器-解码器**结构
（`down_block` 下采样 → `bottleneck` → `up_block` 上采样 + skip connection）。

输入输出很特别：
- **输入**：连续 **8 帧**堆叠（`seq_len=8`），不是单帧。球的运动只有在多帧序列里才能和背景区分。
- **输出**：和原图同分辨率的**热力图（heatmap）**。球所在像素是高斯亮斑，其它地方为黑。

```
8 帧输入 ──► U-Net ──► 热力图（球的位置 = 亮斑中心）
```

训练损失用 `WBCELoss`（加权二元交叉熵，见 `train.py`）——
亮斑像素极少、背景像素极多，必须加权，否则模型会「全预测黑色」。

### 2.2 从热力图到坐标（predict.py）

`external/TrackNetV3/predict.py` 流程：
1. 热力图 `> 0.5` 二值化。
2. 找连通域、算外接框中心 → 球的 `(cx, cy)`（`predict_location`）。
3. 若全黑（没找到球）→ `Visibility=0`（球被遮挡或飞出画面）。
4. 写入 `41_ball.csv`：`Frame, X, Y, Visibility`。

### 2.3 V3 创新：InpaintNet 坐标补全

球常被运动员身体遮挡、或飞太快丢失几帧。**InpaintNet**（`model.py` 中的 1D 卷积网络）
把 TrackNet 输出的坐标序列当成「有破洞的曲线」，用类似图像修复（inpainting）的方式补全丢失的球位置：
先用 `generate_inpaint_mask` 标出丢球的帧，再根据前后帧把破洞填上（`predict.py` 第 213-228 行附近）。

### 2.4 时序集成（temporal ensemble）

输入是滑窗 8 帧序列，**同一帧出现在 8 个不同窗口里**，每个窗口都给它一个预测。
用 `get_ensemble_weight` 加权平均这 8 个预测 → 大幅降低抖动（`eval_mode='weight'` 模式，`predict.py` 第 170-209 行附近）。

> **训练对象说明**：`train.py` 训的就是这个 U-Net。当前使用预训练权重 `ckpts/TrackNet_best.pt`（约 136MB），
> 平时只跑 `predict.py` 推理，不重新训练。

## 三、管线B：运动员轨迹（YOLOv8-pose + ByteTrack）—— 检测+跟踪范式

全部在 `pipeline_code/overlay_player_analytics.py` 的主循环（约第 1370 行起的 `while True`）。

### 3.1 逐帧流程

**① 检测 + 跟踪**（约第 1490-1513 行）
```python
results = model.track(source=detect_frame, persist=True,
                      tracker='bytetrack.yaml', classes=[0], ...)
```
- `YOLOv8s-pose` 检测画面里所有「人」（`classes=[0]`），同时输出 **17 个 COCO 骨骼关键点**。
- `ByteTrack` 给每个人分配**稳定的 track_id**，跨帧关联（1 号球员始终是 1 号，不跳号）。
- `persist=True` 让跟踪器记住上一帧状态。

**② ROI 裁剪加速**（约第 1497 行）
只在球场附近区域跑检测（`detect_on_court_roi`），减少计算量、也减少观众席误检。

**③ 算脚点**（`estimate_foot_point`）
```python
foot = bbox 底边中心  # (cx, y2)
```
球员「站在球场上的那个点」。近端与远端使用相同逻辑，不再上抬（历史修复点，见第八节）。

**④ 过滤干扰**（约第 1419-1435 行）
- `is_static_top_track`：长时间静止在顶部 → 判定为线审/裁判，加入黑名单。
- `point_in_quad`：脚点必须落在球场四边形内。

**⑤ 近/远分配**（`assign_players`）
把候选人分成「近端球员」「远端球员」。核心：用**投影网线 ± `side_band_px`** 分上下半区，
再用历史 track_id 和位置做连续性绑定（防止两个球员标签互换）。

**⑥ 丢失补偿**（约第 1481-1508 行）
某帧没检测到球员时：先用**光流（optical flow）**外推位置，再不行就 hold 住上一个点，超阈值才重置。

**⑦ 画轨迹**（`draw_trail`）
历史脚点连成线，用 **Catmull-Rom 样条**平滑、画成虚线；
`split_valid_segments` 在异常跳变处断开，避免画出错误的长直线。

## 四、连接两个世界的桥梁：单应性变换（Homography）

整个系统**最重要的数学工具**，对 VR 方向尤其关键。

### 4.1 它解决什么问题

摄像机斜拍，画面里的球场是**梯形**（近大远小）；真实球场是 6.1m × 13.4m **矩形**。
单应性是这两者的映射：

```
画面像素坐标 (px,py)  ◄──── homography ────►  真实球场坐标 (x_m, y_m)
   斜视梯形                                      俯视矩形
```

代码（`run()` 约第 1213 行）：
```python
homography, _ = cv2.findHomography(court_quad, dst)
# court_quad = 画面里球场 4 个角（如 352,232,...）
# dst = [[0,0],[6.1,0],[6.1,13.4],[0,13.4]]  真实米制矩形
```

### 4.2 三个用途

1. **`to_court_m()`**：球员脚点（像素）→ 真实米坐标 → 算**速度、距离、跑动区域**（前/中/后场占比）。
   没有它，画面里「移动 10 像素」在远端和近端代表的真实距离完全不同。
2. **小地图（mini-court）**：`draw_mini_court` 把双方投影成俯视图上的两个点 —— 简化版「VR 俯视战术图」。
3. **几何判断**：球的落点、中线位置等。

> **这就是「展平场地」**。`findHomography` + `to_court_m` 把斜视图展平成俯视矩形。
> 注意：主画面上的球员轨迹是**直接在像素空间**画的；展平只用于统计和小地图。

## 五、渲染与分析层（成片中的所有图层）

主循环每帧最后叠加：

| 图层 | 实现 | 说明 |
|------|------|------|
| 球员脚下轨迹（紫/橙虚线） | `draw_trail` | 近端紫色、远端橙色 |
| 球员骨架 | `draw_skeleton` | 17 关键点连线（`--no_draw_pose` 可关） |
| 左上统计面板 | `draw_stats_panel` | 回合数、距离、均速 |
| 右侧小地图 | `draw_mini_court` | 俯视战术图 |
| 底部速度趋势/加速度/回位计时 | `draw_bottom_widgets` | 用米制速度算 |
| 中文文字 | `draw_text_cn` | 用 PIL 画（OpenCV 不支持中文） |
| 回合分割 | `MotionStats` + ball_csv | 球连续可见=回合中；球长时间丢失+球员静止=回合结束 |

**羽毛球轨迹在此融合**：`41_ball.csv` 读入 `ball_dict`，用于回合切分和小地图球点。

## 六、完整数据流

```
41.MP4
  │
  ├─► [TrackNetV3 U-Net] 8帧→热力图→坐标→[InpaintNet补全] ─► 41_ball.csv
  │
  └─► [主循环 overlay_player_analytics.py] 每帧:
        ① YOLOv8-pose 检测人 + ByteTrack 跟踪 → track_id + 框 + 17关键点
        ② 脚点 = bbox 底边中心
        ③ 过滤裁判/观众
        ④ 近/远球员分配（网线分区 + 历史绑定）
        ⑤ 丢失时光流补偿
        ⑥ Homography: 像素脚点 → 真实米坐标 → 速度/距离/区域
        ⑦ 叠加: 轨迹+骨架+统计面板+小地图+速度图+球轨迹(读csv)
        │
        └─► 41_analysis.mp4
```

## 七、AI+VR 方向扩展提示

**可直接复用到 VR 的资产：**
- **Homography 是 VR 的核心**：已能把任意球员位置映射到真实米制球场坐标。
  VR 里再加一个「米制 → 3D 世界坐标」映射（含身高/Z 轴），即可把真人动作搬进虚拟球场。
- **17 个 COCO 关键点**（现已计算，只是 `--no_draw_pose` 关了渲染）是驱动虚拟角色骨骼（avatar rigging）的输入，动作捕捉的基础。
- **小地图俯视投影**是 VR 战术复盘视角的二维原型。

**做 VR 需要补强的：**
- **深度/3D**：现在全是 2D，VR 需要 Z 轴。方向：单目深度估计，或用关键点 + 人体先验反推 3D 姿态（VideoPose3D、MotionBERT 等）。
- **多视角**：单摄像机有遮挡和透视歧义，理想是多机位融合。
- **实时性**：现在离线处理（约 8 分钟/视频），VR 交互需实时，需上 CoreML/TensorRT。

**如何更高效地协作（经验沉淀）：**
1. **明确「哪一半」**：羽毛球(TrackNet) 还是运动员(YOLO)，原理不同、方案不通用。
2. **用帧/秒数定位问题**：可抽帧量化验证，比文字描述高效得多。
3. **改动前先验证再全量跑**：已形成「探针测试 → 抽帧确认 → 才生成全片」流程，省大量等待。
4. **VR 从小原型起步**：先做「米制坐标 → 3D」小原型，再逐步扩展，不要一上来要完整 VR 管线。

## 八、历史修复记录（远端运动员轨迹）

排查与修复均通过「探针逐帧打印 → 抽帧目视/量化 → 验证后才全量生成」流程完成。

1. **远端发紫（被误判为近端）**
   - 根因：近/远分池用「投影网线 ± 16px」硬带；远端球员上网救球时脚点跨过网线带被错分，甚至错配成近端（紫色）。
   - 修复：`--side_band_px` 默认 `16 → 45`（探针测得远端命中率从 5/400 帧升至 151/400，零 ID 冲突）。

2. **脚点画在肚子/膝盖而非脚下**
   - 根因①：远端候选脚点被 `far_fallback_lift_ratio=0.22` 上抬 22% 框高。
   - 根因②：远端走了「展平→平滑→反投影回画面」额外往返，覆盖了原始脚点，使绘制点偏移。
   - 修复：远端与近端统一——脚点 = bbox 底边中心（不上抬）；去掉远端的投影/平滑往返，
     `far_draw_pt` 直接用原始脚点进 trail；展平/平滑仅服务于小地图。
   - 验证：量化 `delta=(0,0)`（脚点精确落在 bbox 底边中心）。

3. **已回退的失败尝试**
   - 曾加入「透视身高闸门 + 膝盖外推脚点」试图剔除线审/观众，但身高线性模型在远端外推出负值，
     误删真实远端球员，导致远端轨迹更差，已完全回退。
   - 教训：检测层过滤需在目标区间验证有效范围后再启用；改检测过滤风险高于改平滑/跟踪。

**保留的纯提速改动（不影响精度）**：按需灰度（光流才转灰度）、模型 warmup、`--profile` 计时。

## 九、关键参数速查

| 参数 | 默认 | 作用 |
|------|------|------|
| `--detect_interval` | 1 | 每 N 帧检测一次；1=全精度（远端精度优先勿调大） |
| `--imgsz` | 960 | YOLO 推理分辨率；调小提速但伤远端小目标精度 |
| `--side_band_px` | 45 | 近/远分池的网线带宽（px）；上网救球时绑定正确半场的关键 |
| `--device` | mps | Apple Silicon GPU |
| `--no_draw_pose` | — | 关闭骨架渲染（关键点数据仍计算） |
| `--trail_jump_split_px` | 95 | 轨迹异常跳变断开阈值 |
| `--profile` | — | 打印 推理 vs 渲染 的耗时分解 |
| `--court_points` | — | 画面球场 4 角 `x1,y1,...,x4,y4`（TL→TR→BR→BL） |

**典型运行命令**：见 `pipeline_code/run_generate_video.sh`。
